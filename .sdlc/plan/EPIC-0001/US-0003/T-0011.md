# T-0011: Implementar `Handler` de canales en `internal/channel/handler.go`

## Descripción técnica:
Crear `internal/channel/handler.go` [NUEVO]: struct `Handler` con `NewHandler(svc *Service) *Handler` y métodos `List`, `Create`, `Get`, `Update`, `Delete`. DTOs de request/response con `omitempty` en todos los campos opcionales (SPECS-001.5: nulls no aparecen salvo los slots vacíos de `sources`, que sí se serializan como `null`). Parseo de `{id}` con `mux.PathValue` + `uuid.Parse` (inválido → 400 `validation`). Los errores del servicio se propagan al helper `writeError` (para ello el handler recibe una función `writeErr func(http.ResponseWriter, error)` o el mapeo vive en un paquete compartido — decidir en Implement; el mapeo final es el de T-0004). `POST`→201, `PUT`→200, `DELETE`→204. Tests con `httptest` + servicio real + repo mockeado (`testify/mock`): status code, body JSON y formato de error por cada ruta.

## Criterios de aceptación:
- [ ] Cada ruta devuelve el status y body del contrato SPECS-001.5.1 (incluye `{"channels": [...]}` en lista)
- [ ] `POST` con number duplicado → 409 `{"error":{"code":"conflict",...}}`
- [ ] `GET` con id inexistente → 404 `not_found`; id mal formado → 400
- [ ] `sources` se serializa con las 5 posiciones (nulls incluidos)

- [ ] Tests unitarios de la lógica agregada/modificada en verde (coverage de handlers ≥ 70%)
- [ ] Tests existentes sin romper
- [ ] Lint/type-check sin errores (`go vet` y `gofmt` limpios)
- [ ] Código mergeado tras code review
- [ ] Deployable de forma independiente (sin pasos manuales fuera del pipeline)
