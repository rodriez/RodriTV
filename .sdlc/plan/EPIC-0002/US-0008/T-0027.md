# T-0027: Implementar watcher de config en caliente en `internal/catalog/watch.go`

## Descripción técnica:
Crear `internal/catalog/watch.go` [NUEVO] con `Watcher` (goroutine supervisada por el consumidor): cada `pollInterval` (config `CONFIG_POLL_INTERVAL`, default 15 s; inyectable para tests) relee `ConfigReader.Load` y `ChannelReader.ListEnabled`, compara contra el snapshot anterior y, si hay diff, publica el snapshot nuevo en un canal con buffer 1 (coalescing: si el consumidor no leyó el anterior, se reemplaza). API: `NewWatcher(cfgReader ConfigReader, chReader ChannelReader, interval time.Duration) *Watcher`, `Run(ctx) error` (loop con `time.Ticker`, primera carga inmediata y siempre notificada), `Changes() <-chan Snapshot` donde `Snapshot struct { Config BehaviorConfig; Channels []Channel }`. El watcher NO decide qué hacer con los cambios (eso es del Engine, US-0014); solo detecta y notifica. Ante error de lectura: log warn y reintenta en el próximo tick (no muere).

## Pseudo código:
```
Run(ctx):
    prev = nil
    loop ticker:
        snap = {cfgReader.Load(ctx), chReader.ListEnabled(ctx)}
        si error: slog.Warn; continue
        si prev == nil o snap != prev (reflect.DeepEqual): send coalesced a Changes()
        prev = snap
    <-ctx.Done(): retornar nil
```

## Criterios de aceptación:
- [ ] Dado readers fake estables, `Changes()` emite exactamente 1 snapshot inicial y nada más
- [ ] Dado un cambio de config en el fake, el siguiente tick emite el snapshot nuevo en ≤ interval
- [ ] Dado el canal lleno y otro cambio, el consumidor recibe solo el snapshot más reciente (coalescing)
- [ ] Dado reader que falla, el watcher loguea warn y sigue vivo; al recuperarse el reader, emite snapshot
- [ ] Al cancelar `ctx`, `Run` retorna sin goroutines vivas
