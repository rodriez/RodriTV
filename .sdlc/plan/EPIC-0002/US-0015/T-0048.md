# T-0048: Cablear rutas, healthz real y Engine en `cmd/playlist` (integración final)

## Descripción técnica:
Cierre del servicio. En `cmd/playlist/routes.go` (T-0022): registrar `GET /playlist.m3u`, `GET /channels/{n}/index.m3u8`, `GET /channels/{n}/seg-{seq}.ts`, `GET /logos/{filename}` con los handlers de `streamserver` (T-0047). En `cmd/playlist/main.go` (T-0023): componer el grafo completo — `platform.NewPool` → `catalog.PostgresCatalog` + `catalog.Watcher` → `telemetry.PostgresTelemetry` + `proclog.ProcLogger` → `extractor.Factory` → `Engine` (con factory de `ChannelSupervisor` que construye mixer/slate/sourceprocs por canal) → `streamserver.Handlers` (con `RecordRequest = engine.Scheduler().RecordRequest`) → server. El checker de `/healthz` (stub de T-0022) se reemplaza por el real: 200 solo si DB responde Y `engine.Running()`. `Engine.Run` corre en el errgroup raíz junto al server: si el Engine muere, el proceso entero termina con error (restart del contenedor). Test de integración E2E del binario (testcontainers DB + ffmpeg real si disponible, tag `integration`): canal con source m3u8 apuntando a un `httptest.Server` con playlist/segmentos sintéticos → `GET /playlist.m3u` lo lista → `GET /channels/1/index.m3u8` lo enciende → en ≤ 30 s la playlist del canal tiene segmentos y MEDIA-SEQUENCE creciente.

## Pseudo código:
```
main: deps = construir todo en orden (pool, catalog, watcher, telemetry, proclog, extractores, engine, handlers)
eg, ctx = errgroup.WithContext(signalCtx)
```

## Criterios de aceptación:
- [ ] `/healthz` devuelve 503 si el Engine no está corriendo o la DB cae; 200 en estado sano
- [ ] (integration) Flujo E2E completo: lista → pedido de canal apagado → encendido → playlist con segmentos crecientes en ≤ 30 s
- [ ] Si `Engine.Run` retorna error, el proceso sale con código != 0
- [ ] `SIGTERM` apaga engine (todos los ffmpeg) y server dentro de `SHUTDOWN_TIMEOUT`
