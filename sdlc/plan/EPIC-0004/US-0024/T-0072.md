# T-0072: Crear `scripts/release.sh` con validación de tag semántico

## Descripción técnica:
Crear `scripts/release.sh` [NUEVO] (bash, `set -euo pipefail`, ejecutable). Recibe el tag como primer argumento posicional; valida formato `^\d+\.\d+\.\d+$` y aborta con usage si falta o no cumple. Construye las 3 imágenes desde la raíz del repo con el mismo tag: `docker build -f build/api/Dockerfile -t rodritv-api:<TAG> .`, idém `playlist` y `web` (SPECS-004.3: las 3 imágenes con el mismo tag por release, RFC §7). Además tagea `:latest` cada imagen. Sin registry (SPECS-004.8): el build es local en el servidor; dejar el `docker push` preparado/comentado o detrás de una variable `REGISTRY` opcional sin romper el flujo local.

## Pseudo código:
```
TAG="${1:?usage: release.sh <x.y.z>}"
[[ "$TAG" =~ ^[0-9]+\.[0-9]+\.[0-9]+$ ]] || { echo "tag inválido: $TAG"; exit 1; }
para svc en api playlist web:
    docker build -f "build/$svc/Dockerfile" -t "rodritv-$svc:$TAG" -t "rodritv-$svc:latest" .
si REGISTRY definido: tag + push de las 3 imágenes al registry
imprimir resumen de imágenes construidas
```

## Criterios de aceptación:
- [ ] Sin argumento o con tag `v1.2` / `1.2.x` / `latest`, aborta con código ≠ 0 y mensaje de usage
- [ ] Con `1.2.3`, construye las 3 imágenes tagueadas `rodritv-{api,playlist,web}:1.2.3` y `:latest`
- [ ] Si falla el build de una imagen, el script aborta (no continúa con las siguientes)
- [ ] `shellcheck scripts/release.sh` limpio

## Definición de finalizado (DoD):
- [ ] `shellcheck` sin errores ni warnings
- [ ] Ejecución de prueba con tag de ejemplo verificada en local
- [ ] Tests existentes sin romper
- [ ] Código mergeado tras code review
- [ ] Deployable de forma independiente (sin pasos manuales fuera del pipeline)
