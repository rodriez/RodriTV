# T-0063: Crear página y fragmento de configuración global

## Descripción técnica:
Agregar a `internal/panel/pages.go` el handler `ConfigPage`: `GET /config` → `api.GetConfig` → renderiza `pages/config.html` [NUEVO] (extiende `layout.html`) con el formulario de las 5 claves de SPECS-001.5.3, cada input con validación en cliente según rangos del contrato: `neighbors` (int 0–5), `startup_channels` (int 0–20), `current_channel_ttl_minutes` (int 5–120), `buffer_minutes` (int 1–10), `uptime_threshold` (float 0.5–1.0, step 0.01); error de red → página con banner. Agregar a `internal/panel/fragments.go` el handler `ConfigSaveFragment`: `POST /frag/config` → parseo y validación local de rangos (mismos límites, antes de llamar a la API) → `api.PutConfig` → éxito: fragmento `partials/config_form.html` [NUEVO] re-renderizado con mensaje "Configuración guardada"; 400 → mismo fragmento con `Fields` junto a cada input; red/5xx → banner "API no disponible". Registrar ambas rutas en `cmd/web/routes.go`. Tests con `APIClient` mockeado.

## Pseudo código:
```
ConfigSaveFragment:
    cfg, ferr = parseConfigForm(r) // convierte tipos + valida rangos locales
    si ferr: render config_form{Values, Errors locales}; return
    saved, err = api.PutConfig(ctx, cfg)
    si IsValidation: config_form{Values: cfg, Errors: err.Fields}; return
    si err red: banner; return
    render config_form{Values: saved, OK: "Configuración guardada"}
```

## Criterios de aceptación:
- [ ] `GET /config` muestra los valores efectivos actuales de la API en los 5 inputs con sus `min`/`max`/`step`
- [ ] Dado `uptime_threshold=1.5` en el form, no se llama a la API y el error aparece junto al campo
- [ ] Dado 400 con `fields.buffer_minutes`, el fragmento lo muestra inline sin perder los valores ingresados
- [ ] Dado éxito, el fragmento muestra la confirmación y los valores devueltos por la API
- [ ] Dado error de red, el fragmento muestra el banner "API no disponible"
