# T-0022: Crear servidor HTTP :9290 con middleware y `/healthz` en `cmd/playlist/server.go`

## Descripción técnica:
Crear `cmd/playlist/server.go` [NUEVO] con `NewServer(cfg Config, mux *http.ServeMux) *http.Server` (timeouts: `ReadHeaderTimeout 10s`, `IdleTimeout 120s`; sin `WriteTimeout` global porque los segmentos HLS pueden servir archivos grandes) y `Run(ctx context.Context, srv *http.Server, shutdownTimeout time.Duration) error` con arranque en goroutine, espera de `ctx.Done()` o error de `ListenAndServe`, y `Shutdown` con el timeout configurado. Middleware en `cmd/playlist/server.go`: `withLogging` (slog: método, ruta, status, duración) y `withRecover` (recover → 500 + log con stack). Handler `/healthz` [NUEVO] con dependencia `HealthChecker` (interfaz definida aquí: `Healthy(ctx) bool`): 200 si DB responde Y Engine corre; 503 si no. Por ahora el Engine no existe: registrar una implementación stub inyectada desde main que solo verifica DB (el check de Engine se cablea en T-0048). Registrar la ruta en `cmd/playlist/routes.go` [NUEVO] con pattern `GET /healthz` del ServeMux de Go 1.27.

## Pseudo código:
```
mux.Handle("GET /healthz", healthHandler(checker))
healthHandler: si checker.Healthy(r.Context()): 200 "ok"; si no: 503 "unhealthy"
Run: go srv.ListenAndServe(); select { <-ctx.Done(): srv.Shutdown(timeoutCtx) | err := <-errCh: return err }
```

## Criterios de aceptación:
- [ ] Dado el server levantado con checker sano, `GET /healthz` responde 200
- [ ] Dado checker insano, responde 503
- [ ] Dado un handler que paniquea (registrado solo en test), el middleware recover responde 500 y el server sigue vivo
- [ ] Al cancelar el contexto, `Run` cierra el server dentro del `ShutdownTimeout` sin conexiones colgadas
